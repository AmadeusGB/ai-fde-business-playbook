# Worksheet 14 Accept the reuse of a delivery asset

Use this for one asset and one target purpose. Record differences in conditions first, then check reuse evidence. A blank means unverified, not a pass. See the completed teaching example in Figure 14-13.

| Check | Record for this reuse (complete or link to an attachment) |
|---|---|
| Asset, version, and maintainer | Name: ________  Version: ________  Maintainer: ________ |
| Original purpose → new purpose | Original: ________  New: ________ |
| Inheritable parts / required adaptation | Inheritable: ________  Differences and changes: ________ |
| Required revalidation / explicit exclusions | New material and acceptance conditions: ________  Not for: ________ |
| Reuse by a different team | Team: ________  Evidence identifier: ________  Failures / unresolved items: ________ |
| Original developer support | Intervention and hours: ________  Critical decisions made on the team's behalf?: ________ |
| Version change validation | Change: ________  Affected scope: ________  Retest record: ________ |
| Labor and observation period | Delivery: ____ hours; subsequent work: ____ hours; start and end dates: ________ |
| Unobserved changes / continuing responsibilities | Changes not experienced: ________  Accountable person / check date: ________ |
| This decision | Accept limited scope / additional validation / do not use: ________  Accepting person: ________ |

Instructions: after a failure, correct the asset and retest with new material. Record permitted support; do not count an original developer's guided run as independent completion. Record shared development separately. The former client's data, authorization, and conclusions do not transfer automatically.
